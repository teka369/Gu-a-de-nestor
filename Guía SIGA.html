1Resumen ejecutivo

SIGA es una aplicación web cliente-servidor que centraliza la gestión académica de un centro de formación: usuarios con roles, aprendices, fichas, instructores, sesiones y asistencia. Genera reportes con datos reales de PostgreSQL y los exporta a CSV.

ImportanteEs un proyecto formativo independiente. No es una plataforma oficial del SENA. Se usan solo datos ficticios.

2Alcance de la versión 1

Incluye

  • Login y logout, cambio de contraseña, activar y desactivar cuentas.
  • Cuatro roles: Administrador, Líder académico, Instructor y Consulta, con permisos verificados en el servidor.
  • CRUD de aprendices con búsqueda, paginación y documento único.
  • Fichas, inscripciones y asignación de instructores.
  • Sesiones de formación con validación de horarios y cancelación (no se borran).
  • Asistencia (presente, ausente, tardanza, excusa) con trazabilidad.
  • Reportes con filtros, exportación CSV y dashboard por rol.
  • Pruebas automatizadas, documentación y guía de despliegue.

Queda fuera de la v1

  • Recuperación de contraseña por correo (requiere servicio de correo y tokens seguros). El Administrador restablece contraseñas.
  • Integración con sistemas oficiales del SENA, notificaciones, app móvil nativa y carga masiva.

7Riesgos técnicos y decisiones de seguridad

Riesgos

  • Instalación en Windows: módulos nativos como argon2 pueden fallar; plan B: bcryptjs.
  • Planes gratuitos: pueden cambiar o suspender la app por inactividad. Se verifican en la Etapa 9.
  • Curva de aprendizaje: el alcance es amplio; se trabaja por módulos pequeños.
  • Datos personales: nada de datos reales sin autorización.

Seguridad desde el inicio

  • Contraseñas con Argon2id, nunca en texto plano ni en logs.
  • Secretos en .env (fuera de Git); solo .env.example en el repositorio.
  • SQL siempre parametrizado, sin concatenar datos del usuario.
  • Permisos verificados en el servidor: ocultar botones no es seguridad.
  • Lista blanca de campos y de columnas de ordenamiento.
  • Límite de intentos en el login y cookies HttpOnly + Secure + SameSite.
  • Usuario de BD con mínimo privilegio y mensajes de error genéricos hacia el cliente.

Práctica 1: instalar Git y PostgreSQL

Git

¿Para qué sirve?Git guarda “fotografías” del proyecto (commits). Permite volver atrás si algo se daña y ver qué cambió, cuándo y por qué. La identidad (nombre y correo) queda registrada en cada commit.
  1. Descargar “Git for Windows” desde git-scm.com. Editor por defecto: VS Code; rama inicial: main.
  2. Cerrar y abrir una terminal nueva, y verificar git --version.
  3. Configurar la identidad (con tus datos): 
    git config --global user.name "Tu Nombre"
git config --global user.email "tu-correo@ejemplo.com"
git config --global --list

Los comandos git config no muestran nada cuando funcionan: el silencio es normal.

PostgreSQL

¿Para qué sirve?Es el motor de base de datos de SIGA. Guarda aprendices, fichas y asistencia, y hace cumplir reglas (por ejemplo, que no haya dos documentos iguales). psql es su terminal y pgAdmin su interfaz gráfica.
  1. Descargar el instalador de postgresql.org/download/windows.
  2. Marcar PostgreSQL Server, pgAdmin 4 y Command Line Tools. Puerto 5432.
  3. Definir la contraseña de postgres y guardarla en un lugar seguro. Nunca la compartas en un chat.
Problema: psql no se reconoceEl instalador a veces no agrega la carpeta bin al PATH. Verifica con dir "C:\Program Files\PostgreSQL" (en nuestro caso, versión 18) y agrega C:\Program Files\PostgreSQL\18\bin en Variables de entorno > Path (usuario) > Nuevo. Cierra y abre la terminal.

Verificar el servicio y la conexión

psql -U postgres -h localhost -p 5432
SELECT version();
\q

Debe aparecer ESTADO : 4 RUNNING y luego una línea que empieza con PostgreSQL 18. La advertencia del código de página (850 vs 1252) es normal en CMD.

¿Para qué sirve?GitHub guarda una copia remota del repositorio: es tu respaldo, permite trabajar desde otro equipo y sirve como evidencia del proceso. origin es el nombre del repositorio remoto y push envía tus commits.
  1. En github.com: New repository, nombre siga, visibilidad Private, sin README ni .gitignore.

    git remote add origin https://github.com/TU_USUARIO/siga.git

  3. Autorizar en el navegador cuando Git lo solicite. Nunca escribas tu contraseña en la terminal.

  • Node, npm, Git, PostgreSQL y VS Code responden con versión.
  • El servicio de PostgreSQL está en RUNNING y conecta.
  • La estructura de carpetas existe y git log --oneline muestra el commit.
  • .env no está en Git ni en GitHub.

# Requisitos de SIGA (Sistema de Gestión Académica)

Proyecto formativo independiente de Tecnología en Análisis y Desarrollo de
Software (ADSO). No es una plataforma oficial del SENA ni se integra a sus
sistemas. Durante el desarrollo y las pruebas se usan únicamente datos ficticios.

## 1. Planteamiento del problema

La información académica de aprendices, fichas, sesiones y asistencia suele
llevarse en hojas de cálculo, formatos en papel o archivos separados. Esto
dificulta consultar el historial, detectar inasistencias a tiempo, evitar
registros duplicados y saber quién modificó un dato.

## 2. Justificación

Una aplicación web con base de datos relacional permite centralizar la
información, controlar quién accede a ella según su rol, conservar la
trazabilidad de los cambios y calcular reportes a partir de datos reales. A la
vez, sirve como evidencia de aprendizaje de buenas prácticas de ingeniería de
software.

## 3. Objetivos

**General.** Construir una aplicación web que permita administrar la
información académica de aprendices, fichas, instructores, sesiones y asistencia
desde una plataforma centralizada.

**Específicos.**

1. Implementar autenticación segura y control de permisos por rol verificado en
   el servidor.
2. Gestionar aprendices, fichas, inscripciones e instructores con integridad de
   datos.
3. Programar sesiones de formación y registrar la asistencia con trazabilidad.
4. Generar reportes de asistencia con filtros y exportación a CSV.
5. Documentar, probar y desplegar el sistema usando servicios con plan gratuito,
   cuando estén disponibles.

## 4. Alcance de la versión 1

**Incluye:** autenticación y usuarios, aprendices, fichas, inscripciones,
asignación de instructores, sesiones, asistencia, reportes con CSV, dashboard
por rol, pruebas y documentación.

**No incluye:** recuperación de contraseña por correo, integración con sistemas
oficiales del SENA, notificaciones, aplicación móvil nativa y carga masiva de
datos.

**Limitaciones:**

- Los planes gratuitos de despliegue pueden suspender la aplicación por
  inactividad o cambiar sus condiciones.
- No se garantiza disponibilidad permanente.
- No se debe cargar información real de aprendices sin autorización y sin medidas
  de protección de datos personales.

## 5. Actores

| Actor | Descripción |
|---|---|
| Administrador | Gestiona usuarios, roles y todos los módulos. |
| Líder académico | Administra aprendices, fichas, sesiones, instructores y reportes. |

## Autenticación y usuarios

### HU-01. Iniciar sesión
**Como** usuario registrado, **quiero** iniciar sesión con mi correo y contraseña,
**para** acceder a las funciones de mi rol.
**Cubre:** RF-01, RN-02, RN-16.

Criterios de aceptación:
- Con credenciales correctas y cuenta activa, se crea una sesión y se redirige al
  panel principal.
- Con credenciales incorrectas se muestra un mensaje genérico ("Correo o
  contraseña incorrectos"), sin indicar cuál de los dos falló.
- Una cuenta desactivada no puede iniciar sesión.
- Tras varios intentos fallidos seguidos, el servidor limita temporalmente los
  nuevos intentos.
- La contraseña nunca se muestra ni se registra en los logs.

### HU-02. Cerrar sesión
**Como** usuario autenticado, **quiero** cerrar sesión, **para** proteger mi cuenta
en un equipo compartido.
**Cubre:** RF-01.

Criterios de aceptación:
- Al cerrar sesión, el servidor invalida la sesión y se regresa a la pantalla de
  inicio de sesión.
- Después de cerrar sesión, volver atrás en el navegador no permite ver datos
  protegidos: cualquier solicitud a la API responde 401.
- Si la sesión expira, la interfaz informa al usuario y lo envía al inicio de
  sesión.

### HU-03. Cambiar mi contraseña
**Como** usuario autenticado, **quiero** cambiar mi contraseña, **para** mantener
mi cuenta segura.
**Cubre:** RF-02.

Criterios de aceptación:
- Se exige la contraseña actual y una nueva contraseña con confirmación.
- La nueva contraseña cumple una longitud mínima (propuesta: 10 caracteres) y es
  distinta de la actual.
- Si la contraseña actual es incorrecta, el cambio se rechaza.
- La contraseña se guarda solo como hash.

### HU-04. Gestionar usuarios
**Como** Administrador, **quiero** crear, editar, activar y desactivar usuarios y
asignarles un rol, **para** controlar quién usa el sistema.
**Cubre:** RF-03, RN-03, RN-16.

Criterios de aceptación:
- El correo de cada usuario es único; un duplicado se rechaza con un mensaje claro.
- Solo el Administrador accede a este módulo; cualquier otro rol recibe 403.
- Al desactivar un usuario, no puede iniciar sesión y sus sesiones activas se
  invalidan.
- Un usuario no puede desactivar su propia cuenta de Administrador si es el único
  Administrador activo.

**Como** Administrador, **quiero** restablecer la contraseña de otro usuario,

  2. Helmet, límite de solicitudes y lectura del JSON.
  3. Sesión: sin ella, 401.
  4. Rol: sin permiso, 403.
  5. CSRF en POST, PUT y DELETE.
  6. Validación: datos inválidos, 400 o 422.
  7. Controlador y servicio ejecutan la lógica y el SQL.
  8. Respuesta JSON, o error genérico con detalle solo en el log.

Códigos previstos: 200, 201, 400, 422, 401, 403, 404, 409 (conflicto, por ejemplo documento duplicado), 429 y 500. Formato propuesto: {ok, datos, meta} o {ok:false, error:{codigo, mensaje}} (se fija en la Etapa 5).

Seguridad web

  • Sesión en PostgreSQL; cookie HttpOnly, SameSite=Lax y Secure en producción.
  • CSRF (propuesta): cabecera personalizada y verificación de Origin.
  • CORS limitado al origen de la app.
  • Argon2id; límite de intentos en el login.
  • XSS: textContent en vez de innerHTML con datos del usuario.
  • SQL solo parametrizado; errores genéricos.

## 2. Responsabilidad de cada capa

| Capa | Carpeta | Responsabilidad | Lo que NO debe hacer |
|---|---|---|---|
| Configuración | `backend/src/config/` | Leer variables de entorno y crear la conexión a PostgreSQL | Contener lógica de negocio |
| Rutas | `backend/src/routes/` | Asociar cada URL y método HTTP con su middleware y controlador | Consultar la base de datos |
| Middlewares | `backend/src/middlewares/` | Sesión, verificación de rol, CSRF, manejo de errores | Conocer reglas de un módulo concreto |
| Validadores | `backend/src/validators/` | Verificar y normalizar la entrada, aceptar solo campos permitidos | Escribir en la base de datos |
| Controladores | `backend/src/controllers/` | Leer la petición, llamar al servicio, responder con el código HTTP correcto | Escribir SQL |
| Servicios | `backend/src/services/` | Reglas de negocio, transacciones y consultas SQL parametrizadas | Conocer `req` ni `res` de Express |
| Aplicación | `app.js`, `server.js` | `app.js` arma Express; `server.js` lo arranca | Mezclar ambas tareas |
| Frontend | `frontend/` | Páginas, estilos y scripts que consumen la API | Aplicar permisos como medida de seguridad |

Regla práctica: si cambias una regla de negocio, solo debería cambiar un servicio.

## 3. Ciclo de una solicitud

1. El navegador envía una solicitud a `/api/...` con la cookie de sesión.
2. Express aplica `helmet`, el límite de solicitudes y el análisis del cuerpo JSON.
3. El middleware de sesión identifica al usuario. Sin sesión válida responde 401.
4. El middleware de rol verifica el permiso de la operación. Sin permiso responde 403.
5. Para métodos que modifican datos se verifica la protección CSRF.
6. El validador comprueba los datos. Si son inválidos responde 400 o 422.
7. El controlador llama al servicio, que ejecuta la lógica y las consultas.
8. Si todo sale bien, el controlador responde en JSON. Si algo falla, el manejador
   central de errores responde con un mensaje genérico y registra el detalle en el
   servidor.

```json
{ "ok": true, "datos": {}, "meta": { "pagina": 1, "total": 0 } }
```

```json
{ "ok": false, "error": { "codigo": "VALIDACION", "mensaje": "Texto para el usuario" } }
```

## 4. Estrategia de autenticación y seguridad web

| Aspecto | Decisión | Motivo |
|---|---|---|
| Sesión | Guardada en PostgreSQL (D2) | Permite revocarla al cerrar sesión o desactivar la cuenta (RN-16) |
| Cookie | `HttpOnly`, `SameSite=Lax`, `Secure` en producción | JavaScript no puede leerla; se reduce el riesgo de XSS y CSRF |
| CSRF (propuesta) | Cabecera personalizada obligatoria en `POST`, `PUT` y `DELETE`, más verificación del encabezado `Origin` | Una página de otro sitio no puede enviar esa cabecera sin permiso de CORS |
| CORS | Restringido al origen de la aplicación | Con D1 casi no hay solicitudes entre orígenes |
| Contraseñas | Argon2id (alternativa: bcrypt) | Nunca se guardan en texto plano |
| Fuerza bruta | Límite de solicitudes en el inicio de sesión | Reduce los intentos masivos |
| XSS | El frontend usa `textContent` para datos del usuario y evita `innerHTML` con ellos | Evita ejecutar código inyectado |
| SQL | Solo consultas parametrizadas | Evita inyección SQL |
| Errores | Mensaje genérico al cliente, detalle en el registro del servidor | No revela información interna |

## 3. Normalización

- **1FN:** todas las columnas guardan valores simples; no hay listas dentro de una celda.
- **2FN y 3FN:** los datos de personas viven una sola vez (`usuarios`,
  `aprendices`). Las relaciones muchos a muchos usan tablas intermedias, y los
  atributos de cada tabla dependen de su propia clave.
- **Desnormalización deliberada:** `fichas.programa` es texto repetido entre
  fichas del mismo programa. Una tabla `programas` queda como mejora futura.
- **Auditoría:** `datos_antes` y `datos_despues` son `jsonb` para guardar el
  cambio sin crear una tabla de historial por entidad. Nunca incluyen contraseñas
  ni hashes.

## 4. Integridad referencial

- Todas las claves foráneas usan `ON DELETE RESTRICT`: como no se borra
  físicamente (D3), un intento de borrado falla en lugar de dejar huérfanos.
- La baja se hace con `activo`, `estado` o `activa`.
- Las claves primarias son enteros de identidad generada por la base de datos.

## 7. Estrategia de migraciones

1. Los cambios de esquema se escriben como archivos SQL numerados en
   `database/migrations/` (por ejemplo `001_roles_usuarios.sql`).
2. Una tabla `schema_migrations` guarda cuáles ya se aplicaron.
3. Un script sencillo (`backend/src/config/migrate.js`) aplica en orden las
   pendientes, cada una dentro de una transacción.
4. **Una migración aplicada no se edita.** Un cambio nuevo es un archivo nuevo.
5. No se escriben migraciones de reversa en la v1; si algo sale mal en un entorno
   se restaura el respaldo (`pg_dump`) y se corrige la migración.
6. Los datos ficticios viven en `database/seeds/` y nunca se cargan en producción
   con contraseñas conocidas.
